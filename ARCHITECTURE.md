# Architecture

A static Vue SPA with no backend. All "server" logic happens once, at build
time, in a TS pipeline; everything after that is a browser talking to
`localStorage`. For the fuller history and rationale behind these choices,
see `AGENTS.md` and `bd show ami-fcq`.

## Data flow

```
source PDFs (private, gitignored)
        │  one-time extraction, already done — see "Why no Python pipeline" below
        ▼
frozenOutput.json  (packages/pipeline/src/__tests__/fixtures/)
        │  packages/pipeline/src/colorRecords.ts  — classifies raw color text
        │  packages/pipeline/src/buildCatalog.ts  — joins tracker+crosswalk+materials,
        │                                            validates against packages/schema
        ▼
packages/web/src/data/patterns.json  (build artifact, gitignored, regenerated by CI)
        │  static import at build time
        ▼
packages/web  (Vue 3 + Pinia + vue-router, deployed to GitHub Pages)
        │  haveIt / completed / notes / stash — the only things the app itself writes
        ▼
browser localStorage  (per-device, versioned JSON blob — see packages/schema's
                        UserStateStore)
```

`packages/schema` sits beside this flow rather than in it: both the pipeline
and the web app import the same Zod types (`Pattern`, `MaterialRow`, `Stash`,
...), so a shape mismatch between what the pipeline produces and what the app
expects fails loudly at build time (`Catalog.parse()` in `buildCatalog.ts`,
`vue-tsc` in CI) instead of silently at runtime.

## Why catalog data is a build artifact, not a live backend

There's exactly one user (Caleb) and the catalog changes only when new
patterns are added — not per-request, not per-user. Running a database and
an API for that would be pure overhead: cost, an attack surface, something to
keep patched. `patterns.json` is regenerated by `pnpm --filter
@amigurumi/pipeline run build:catalog` and committed to the deploy artifact
by CI (see `.github/workflows/deploy.yml`), not checked into git — it's
derived data, same as a compiled binary.

## Why user state is client-only

`haveIt`, `completed`, notes, and the yarn stash are personal tracking data
for one person on their own devices. There's no multi-device sync
requirement, no sharing, no reason to hold anyone's data on a server —
`localStorage` is simpler, free, and private by construction. The tradeoff
(no cross-device sync, wiped if the browser storage is cleared) was accepted
explicitly; see the epic for the alternatives considered.

## Why there's no Python pipeline in this repo

An earlier version of this project used a Python script to extract materials
data from all 654 existing pattern PDFs (see AGENTS.md's "PDF structure" and
"Reconciliation methodology" sections for what that involved — OCR, layout
detection, fuzzy name matching). That extraction is a one-time job: it's
already been run, reviewed, and corrected by hand once. Keeping the Python
code around to re-run it would mean maintaining a second, unmaintained
language/toolchain in a TypeScript monorepo for a job that doesn't need
repeating. Its output was instead frozen as
`packages/pipeline/src/__tests__/fixtures/frozenOutput.json` — the
regression baseline every TS pipeline change is tested against — and the
Python code deleted. A TS-based extractor for *future* new patterns
(`extractText`/`extractOcr`/`parseMaterials`) is separately scoped, not yet
built (`bd show ami-fcq.10`).

## Packages

- `packages/schema` — shared Zod types; the single source of truth for what
  a `Pattern` looks like, imported by both packages below.
- `packages/pipeline` — Node/TS, no runtime dependency on the web app.
  Classifies colors, builds the catalog, is unit-tested against the frozen
  fixture (`pnpm --filter @amigurumi/pipeline run test`).
- `packages/web` — Vue 3 + Vite + TS, no runtime dependency on the pipeline
  beyond the JSON file it produces. Hash-based routing
  (`createWebHashHistory`) because GitHub Pages has no server-side rewrite
  rule for a path-based SPA.

## CI/CD

`.github/workflows/ci.yml` runs typecheck + test on every push/PR.
`.github/workflows/deploy.yml` triggers on `ci.yml` *completing
successfully* (`workflow_run`, gated on `conclusion == 'success'`) — not
merely after it by coincidence — rebuilds the catalog and the web app, and
publishes to GitHub Pages.
